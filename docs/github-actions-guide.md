## 🎯 1. فلسفة الأتمتة وهندسة العمل التشغيلي (CI/CD Philosophy)

في المشاريع الكبيرة (Enterprise-Grade)، يتم فصل بيئة كتابة الكود وتوليده (والتي يمثلها هنا وكلاء الـ AI وعمليات التطوير الموضعية) تماماً عن بيئات الفحص الفعلي والترحيل للإنتاج والتجميع المباشر. 

يتحول مستودع **Cortex AI** بموجب هذا التصميم الهيكلي إلى مشروع مؤتمت بالكامل حيث يتولى خادم **GitHub Actions** الصلاحيات والمسؤوليات التشغيلية التلقائية للفحص وحقن الجداول والنشر السحابي، مع الإبقاء على سلامة الفرع `arena/019fa52b-dlp2026` ومنع التعديلات العشوائية.

## 🛠️ 2. هيكلية ملفات الأتمتة المعرفة (Workflow Architecture)

تم تأسيس 5 ملفات أتمتة متطورة للغاية تحت المسار المخصص `.github/workflows/`:

```text
.github/workflows/
├── quality.yml           # تدقيق التنسيق، الجودة، وفحص ثغرات الحزم (تلقائي)
├── test.yml              # تشغيل حزمة الاختبارات الـ 11 بالكامل (تلقائي)
├── build.yml             # التحقق من بناء Next.js ومخطط بريسما (تلقائي)
├── database-migrate.yml  # ترحيل الجداول لـ Supabase (يدوي صامت ومحمي)
└── deploy.yml            # بناء ونشر الأصول السحابية لـ Vercel (يدوي ومؤمن)
```

### أ. تفصيل مسارات التشغيل والمسؤوليات:

| سير العمل (Workflow) | المشغل (Triggers) | المهام المنفذة (Key Actions) | مستويات الخطورة والإحباط |
| :--- | :--- | :--- | :--- |
| **`quality.yml`** | `push` / `pull_request` | فحص التنسيق لـ Prettier، تشغيل مفسر الأخطاء ESLint، فحص الأنواع الصارم لـ TypeScript tsc، وفحص أمان الحزم. | **إحباط فوري** في حال وجود أي خطأ تشريحي أو لغوي. |
| **`test.yml`** | `push` / `pull_request` | تشغيل كافة الحزم الاختبارية الـ 11 المترابطة بالتوالي لجميع أركان التطبيق. | **إحباط فوري** في حال فشل أي اختبار تشغيلي، مع رفع سجلات الأخطاء كأصول (Artifacts). |
| **`build.yml`** | `push` / `pull_request` | فحص بنية مخطط Prisma وتجميع ملفات Next.js 15 الإنتاجية للتأكد من خلو المشروع من أخطاء التوجيه أو الاستيراد الترانزيتي. | **إحباط فوري** وتأمين بيئة الإنتاج من الانهيار. |
| **`database-migrate.yml`** | **`workflow_dispatch`** (يدوي حصراً) | قراءة السيكويل التأسيسي وضخه مباشرة لقاعدتك السحابية في Supabase عبر `npx prisma migrate deploy`. | **يدوي بالكامل** ومحمي بكلمة تأكيد إلزامية لتفادي أخطاء النقر الخاطئ. |
| **`deploy.yml`** | **`workflow_dispatch`** (يدوي حصراً) | سحب البيانات التشغيلية، بناء الأصول في Vercel، ورفع النظام حياً للإنتاج التام. | **يدوي بالكامل** ويشترط تخطي مهام الجودة والاختبارات بنجاح. |

## 🔑 3. إدارة المتغيرات الرمزية والسرية (GitHub Secrets Management)

للحفاظ على أعلى درجات الحماية وتطبيق معايير الامتثال والملاحظة الأمنية، يجب تزويد خادم المستودع في GitHub بالمتغيرات السرية التالية تحت الرابط:  
`Settings ➔ Secrets and variables ➔ Actions ➔ Repository Secrets`

| اسم المتغير (Secret Key) | طبيعة الاستخدام (Purpose) | أين وكيف يتم استخراجه؟ (Extraction Source) |
| :--- | :--- | :--- |
| **`DATABASE_URL`** | ترحيل وتحديث بيانات الجداول سحابياً عبر منفذ مجمع العمليات التبادلية `6543`. | Supabase Dashboard ➔ Project Settings ➔ Database ➔ URI (Pooler Option). |
| **`DIRECT_URL`** | تمرير عمليات التهيئة الإدارية وتجاوز pgBouncer عبر منفذ سيكويل المباشر `5432`. | Supabase Dashboard ➔ Project Settings ➔ Database ➔ URI (Direct Option). |
| **`NEXT_PUBLIC_SUPABASE_URL`** | العنوان السحابي والـ API الرئيسي لربط المتصفح وخوادم Edge بـ Supabase. | Supabase Dashboard ➔ Project Settings ➔ API ➔ Project URL. |
| **`NEXT_PUBLIC_SUPABASE_ANON_KEY`** | المفتاح العام المسموح بتداوله في المتصفح لمصادقة عمليات الدخول والتحقق للعملاء. | Supabase Dashboard ➔ Project Settings ➔ API ➔ `anon` `public` API Key. |
| **`SUPABASE_SERVICE_ROLE_KEY`** | المفتاح السري الخلفي الخارق لتخطي جدر RLS للأمور الإدارية والأمنية والـ SRE. | Supabase Dashboard ➔ Project Settings ➔ API ➔ `service_role` Private Key. |
| **`OPENAI_API_KEY`** | تشغيل وتوجيه بوابات معالجة الذكاء الاصطناعي وصناعة الأهداف المباشرة لـ OpenAI. | OpenAI API Keys Dashboard ➔ Create New Secret Key. |
| **`VERCEL_TOKEN`** | مفتاح التخويل الشخصي العابر للحدود للسماح لـ Actions ببناء الأصول في خوادم Vercel. | Vercel Account Settings ➔ Tokens ➔ Create Personal Access Token. |
| **`VERCEL_ORG_ID`** | المعرف الرقمي للمؤسسة أو حساب المالك المستضيف للتطبيق في Vercel. | يتم استخراجه من مجلد التجميع المحلي للمشروع أو لوحة بيانات المستخدم في Vercel. |
| **`VERCEL_PROJECT_ID`** | المعرف الرقمي الفريد للمشروع المستهدف تحديثه بالمنصة. | يتم استخراجه من صفحة إعدادات المشروع (Project Settings) في Vercel. |

## 🛡️ 4. قواعد حماية الفروع وتأمين الإنتاج (Branch Protection Rules)

لمنع أي تجاوز أو دفع عشوائي مباشر لكود الإنتاج وإلزام المطورين بالعبور عبر صمام الأمان والتحقق التلقائي، يُوصى بتهيئة القواعد التالية في GitHub تحت الرابط:  
`Settings ➔ Branches ➔ Add Branch Protection Rule`

### أ. فروع الحماية الموصى بها:
* **`main`**: فرع الإنتاج الرئيسي والحاسم.
* **`arena/019fa52b-dlp2026`**: فرع الاستقرار للنسخة التجريبية الحالية (Branch Candidate).

### ب. القواعد الأمنية الواجب تفعيلها يدوياً (SRE Recommended Settings):
1. **Require a pull request before merging (إلزامية طلبات السحب):**
   * تفعيل هذا الخيار يمنع أي مطور أو وكيل ذكاء اصطناعي من الدفع المباشر للفرع (`git push` محظور كلياً للإنتاج)، ويلزمهم بفتح Pull Request للمراجعة والمصادقة المزدوجة.
2. **Require status checks to pass before merging (إلزامية الفحوصات الآلية):**
   * اختيار هذا البند يلزم طلب السحب بتخطي كافة خطوات الجودة والاختبار والتجميع بنجاح تام:
     * `Code Quality Audit` (من ملف `quality.yml`)
     * `Run Automated Tests` (من ملف `test.yml`)
     * `Verify Production Build` (من ملف `build.yml`)
3. **Require branches to be up to date before merging:** لتفادي أي تضارب برمجية ناتجة عن تغيرات سابقة.
4. **Block force pushes (حظر الدفع القسري):** تفعيل هذا البند يمنع استخدام خيار `--force` الذي يتيح إعادة كتابة سجل التغييرات أو مسح التعديلات السابقة.
5. **Block deletions (حظر حذف الفروع):** حماية الفروع التأسيسية من الحذف العرضي أو الخبيث.

## 🚨 5. دليل إدارة الأخطاء واستراتيجيات التراجع (SRE Disaster Playbook)

### أ. كيفية التصرف عند فشل ترحيل قاعدة البيانات (Migration Failures):
1. **أخطاء التبديل والرموز:** إذا ظهر خطأ اتصال، تأكد من تشفير الرموز الخاصة في كلمة المرور أو تغييرها لرموز بسيطة في لوحة تحكم Supabase.
2. **تعارض المخطط وتوقف الـ Deployment:** إذا علقت عملية الهجرة في منتصفها، قم بإعلان تراجع يدوي في محطتك الطرفية لفتح القفل وإعادة المحاولة:
   ```bash
   npx prisma migrate resolve --rolled-back "20260727204500_init_cortex_db"
   ```
3. **التراجع الجراحي السحابي:** إذا أثرت الهجرة على بيانات قائمة، اذهب فوراً لقسم النسخ الاحتياطية (Backups) في Supabase واستعد نسخة آخر ساعة المستقرة (RPO: 1 Hour) بضغطة زر واستعادة التطبيق في أقل من 15 دقيقة (RTO: 15 Minutes).

### ب. كيفية التراجع الفوري عن النشر السحابي (Deployment Rollbacks):
1. **التراجع عبر Vercel (أقل من 5 ثوانٍ):** اذهب إلى لوحة تحكم Vercel، افتح قائمة النشرات السابقة (Deployments)، اختر آخر نشر مستقر تماماً واضغط على خيار **Promote to Production**. سيقوم خادم CDN العالمي لـ Vercel بتحويل حركة مرور المستخدمين للنسخة السابقة فوراً وبلا أي زمن توقف للمنصة.
2. **تفعيل جدار الأمان الهجين للمحاكي (Emergency Mock Switch):** في حال حدوث عطل غير متوقع في قنوات الاتصال السحابية، اذهب لقسم متغيرات البيئة في Vercel، غيّر العلم صراحة إلى **`USE_MOCK=true`** واضغط **Redeploy**. سيعود التطبيق للعمل محلياً بالاعتماد على قواعد البيانات الوهمية الماكيتية المعزولة والمستقرة 100% لحين معالجة المشكلات السحابية بآمان وهدوء.
